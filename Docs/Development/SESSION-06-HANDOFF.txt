3. 완료한 규칙
저장 형식/안전성:
- 단일 profile-v1.json에 schemaVersion1, revision, SHA256 checksum, 진행 유무/체크포인트, 영구 기록과 미지급 완료 기록을 함께 저장. 암호화 없음.

- 주 파일 손상 시 검증된 .bak로 복구. 손상 원본은 읽을 때 수정하지 않으며, 다음 성공 쓰기 전에 preserved/에 바이트 그대로 따로 보존. 유효 백업도 없으면 영구 기록을 추정 초기화하지 않고 저장 불가 상태를 안내.

경계/복원:

5. 데이터·API·이벤트 계약
- 자세한 스키마와 마이그레이션 원칙은 SESSION-06-SCHEMA.txt. schema-example.json은 실제 테스트에서 쓴 가상 코인/장비·경계 데이터 예제이며 사용자 실제 저장이 아님.
- SaveStore.Load: Missing(새 빈 문서), Ready, Recovered(유효 백업), Corrupt, Unsupported, IoError. Usable인 경우만 SaveManager가 문서를 복제하여 변경. Load 자체는 파일을 수정/삭제하지 않음.
- hasCheckpoint가 진행 유무의 권위값. Unity JsonUtility는 null 클래스를 빈 기본 객체로 직렬화할 수 있으므로 checkpoint 객체 존재만으로 이어하기를 판단하지 말 것. Store 읽기/복제에서 false면 null로 정규화.
- checksum은 checksum 필드를 빈 문자열로 둔 JsonUtility 정규 JSON의 UTF8 SHA256. 들여쓰기·필드 값의 직렬화 기준은 SaveStore를 통일해 사용. 외부 편집 파일을 신뢰하지 않음.
- SaveManager.CurrentRunId는 새 게임마다 GUID, 이어하기는 같은 ID. stageData=null이면 기존 검증 도구처럼 저장 비활성. public Store는 저수준 저장 도구, 게임 서비스는 검증/복제/트랜잭션이 있는 SaveManager API를 사용.
- RequestBoundary(kind): 명시적 소유자 판정/보스 경계에서 호출. CheckpointSaved/Restored는 관찰용. 저장은 LateUpdate 순서1000, 리필 전 스냅샷/파일 쓰기를 이벤트 구독자가 중복 구현하지 말 것.
- Capture/ValidateRuntime/TryRestoreCheckpoint/HasCurrentCheckpoint/BeginNewRun/ClearCurrentCheckpoint/CompleteCurrentRun. Restore는 검증 후 GameManager.RestorePhase(IsResuming)→진행/재도전→HP·효과·점수→러너/보스→보드/요구 색→난수 순으로 연결.
- RestorePhase는 복원 단계로 전환할 뿐 새로운 BossAppeared를 발행하지 않음. Boss.RestoreBoundary는 HP/페이즈/그로기 HUD 정보만 발행, PatternResult/실패 피해를 반복하지 않음.
- Boss.CaptureBoundary는 사용하지 않는 전환 타이머를0으로 정규화. 패턴 실행 중간은 저장 경계가 아니며 nextSequence가 없는 불완전 단계로 저장하지 말 것.
- PuzzleBoardManager.RestoreTiles는 명시적 위치/색/State/ItemType으로39칸 복원 후 스케일 연출을 정리, 요구 색 최소 쌍을 검증/확보. 임의 난수로 보드를 새로 생성하는 복원이 아님.
- RulesSignature는 Stage의 거리/속도/피해/장애물/감소값과 Balance/Boss 설정의 서명. 규칙이 달라진 진행은 자동 이어하기하지 않고 원본 보존/새 게임으로 분리. 영구 기록은 유지.
- 현재 maxHP 검증은 Balance.maxStamina와 비교. 세션07에서 장비 능력치가 적용되면 실제 유효 최대HP 및 규칙 서명/호환 정책과 함께 수정해야 함. 이 세션의 가상 장비 레코드가 실제 능력치에 이미 연결된 것은 아님.
