4. 보상·저장·API·이벤트 계약
- SaveManager.CompleteCurrentRun: runId별 PendingClear를 먼저 내구 저장하고 진행 제거. 중복 완료는 쓰기 없음.
- GameManager.TriggerStageClear: 완료 기록 후 ProgressionService.RecoverPending, 다음 Result. Main 시작에서도 RecoverPending으로 완료 직후 앱 중단을 회복. 결과 이벤트 재발행 자체는 지급 근거가 아님.
- ProgressionService.ApplyReward(runId): 최신 문서 읽기/복제→미지급 및 미영수증 확인→고정 코인+선정 장비+ClearRecord.cleared/firstRewardGranted/bestScore+rewardReceipts+PendingClear 제거를 같은 원자 저장에 커밋.
- instanceId는 reward-<runId>, dataId는 고정 장비 ID. 기존 스키마 필드만으로 지급 결과를 재표시하므로 저장 버전 추가/추정 변환 불필요.
- 지급 완료 전 미지급 기록과 실제 지급/클리어 완료는 구분. 지급 파일 교체가 실패하면 기존 영구 기록·PendingClear가 남고 다시 같은 추첨으로 시도. 테이블/장비 데이터 오류·미지원 파일·코인 overflow도 지급 완료로 기록하지 않음.
- 보상과 완료 플래그는 반드시 단일 문서로 처리. UI에서 별도로 코인 추가/장비 생성 금지. 기존 범용 SaveManager.TryApplyReward는 호환 API로 남지만 활성 게임 보상은 ProgressionService만 사용.
- ProgressionService.Read/Stats/ChangeEquipment/Upgrade/NewRunSetup/ApplyReward/RecoverPending/RewardSummary. 모든 서비스 변경은 최신 문서 복제→조건 검증→SaveStore.Write. 공유 캐시·DontDestroyOnLoad 성장 객체 없음.
- Changed 이벤트는 성공한 서비스 커밋 뒤 발행. GameReadyPanel은 활성 수명에서 구독/해제해 CONTINUE/NEW GAME 문구를 갱신. GameHUD도 준비 상태의 현재 장비 최대HP 미리보기를 갱신하고 Start 시 Balance 기본100으로 덮어쓰지 않음. GameEvents 기존 의미와 Item/Match 이벤트 유지.
- EquipmentPanel은 씬 소유, Main의 RectTransform 부모에서는 캔버스를 전체 stretch하고 overrideSorting 사용. Game의 일반 Transform 부모에서는 독립 Canvas 크기 사용. 로비/결과 창 종료·씬 파괴 뒤 구독/참조 유지 금지.
- API는 현재 단일 메인 스레드 게임용. 다중 프로세스가 같은 저장소에 동시에 쓰는 잠금/서버 동기화는 구현 범위 아님.

9. 직접 재현
- 일반 Play는 실제 사용자 저장소를 사용하며 검사 전용 Lv5 장비를 주입하지 않음. 검사 스크린샷의 테스트 자산이 일반 Play에 없다는 것은 정상.
- Main→Play→NEW GAME→빨강/파랑/노랑 요구 장애물→보스 타임어택 순서→그로기 매칭으로 처치. 결과100코인+Trail Hat, EQUIPMENT→EQUIP→UPGRADE100으로 Lv2/코인0, CLOSE→RETRY에서 HP110 확인.
- 이후 클리어마다100코인, 첫 장비 재확정 없이 단일30% 장비 추첨. 강화 비용150/200/250까지 총700 사용 후 Lv5이며 추가 비용 차감 없음.
- 진행 저장 뒤 Home→EQUIPMENT에서 변경 잠금 확인. CONTINUE는 기존 장비/경계를 복원, NEW RUN SETUP 명시 클릭은 진행만 폐기하고 성장 보존. 새 시작 시 현재 장비 능력치 반영.
